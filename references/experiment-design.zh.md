# 实验设计

**这一页是干什么的**：教你怎么设计一次实验，让"变快了"这个结论真的能立住。也告诉你每个批次该留下哪些记录，免得六周后自己都说不清当时是怎么跑的。

**什么时候看它**：
- 你要开一批新实验的时候。
- 你要决定跑哪几组、跑几轮、跑几个种子的时候。
- 你要写 `meta.txt` 的时候。
- 你要在共享服务器上起长任务的时候。
- 你有一个批次跑废了、要处理它的时候。

**臂（arm）是什么**：把一组配置整体叫一个"臂"。像一次对照试验里的几组病人，每组吃一种药，最后对比。

---

## 1. 臂与控制组

**做什么**：一个批次里，除了你要测的那一组，还要有对照。

每个批次都包含：

- 处理臂（treatment：真正要测的那一组）；
- 至少一个安慰剂臂/相同臂（placebo / identical：同样的代码，只换个标签），用来量运行间地板（run-to-run floor：同一份代码跑两遍也会有的差距）；
- 当主张是关于一个估计（estimate：比如"能提升多少"）时，需要 oracle 臂（oracle arm：一个"上帝视角"的对照，它每次都能选到最优，所以它划定了任何排序方式能达到的上限）。

**例子**：Sarathi-Serve（OSDI 2024）把预填充（prefill：读入整段输入）切成小块，让解码（decode：一个一个吐字）不被堵住。如果你要复现它，一个批次可以这样排：
- 处理臂＝切块预填充；
- 相同臂＝切块预填充，只是标签写成另一个名字；
- oracle 臂＝一个能预知每个请求长度的调度器，它给出上限。

给那个**无法**对自变量（independent variable：你故意改动的那一样东西）作出反应的臂命名。如果没有这样的臂，这个设计就无法把信号从噪声中分出来。

**为什么**：没有对照，你测到的可能只是机器当天的状态。

---

## 2. 预登记判据

**做什么**：运行之前，在批次头部写死四件事。这叫预登记（pre-register：先写标准，再跑实验）。

- P1..Pn：机制得到支持所必须成立的条件；
- 每个指标的地板（floor：同一个东西跑两遍也会有的波动幅度）；
- 什么算作"无法区分"；
- 聚合约定（用哪个中位数、分析哪些轮次）。

**例子**：开跑前写："P1：在 70% 负载以上，处理臂的 P99 延迟中位数低于相同臂的地板。"
跑完发现 P1 没成立，但平均吞吐变好了。这时不能把判据改成"平均吞吐"，然后说这次通过了。

运行之后，判据不能新增。一个在不同指标上触发的判据不算数。

**为什么**：跑完再挑判据，等于先射箭再画靶。

---

## 3. 批次清单

**做什么**：每个批次都写一个 `meta.txt`，把这次跑的来龙去脉记下来。

```
script, git commit, date, OUT, N, K, load/rho, model, quantization,
seeds, rounds analysed, environment (engine version), expected model
```

各字段的意思：

- `script`：跑的是哪个脚本。
- `git commit`：代码的哪一个版本。
- `date`：日期。
- `OUT`：输出目录。
- `N`、`K`：这次实验的两个参数，填脚本里实际的取值。
- `load/rho`：负载水平，rho 是负载率。
- `model`：模型名。
- `quantization`：量化方式（把权重压成低精度，省显存）。
- `seeds`：用了哪些种子（seed：随机数种子，固定它就把随机性固定住）。
- `rounds analysed`：分析了哪几轮。
- `environment (engine version)`：运行环境，含引擎版本。
- `expected model`：你声明这次应该加载的模型，用来和实际加载的对账。

批次无法观测到的任何东西（模型、引擎标志）都必须**声明、在启动前守卫、并记录**。

守卫方式：启动前查一下引擎的 `/v1/models`，不一致就拒绝运行。

**例子**：你以为这次加载的是 Llama-3-8B，其实是上一份缓存里的 70B。批次自己看不出来。先查 `/v1/models`，对不上就退出，这一批就白跑了，但不会白写进论文。

**为什么**：六周后你不记得那天加载的是哪个模型，`meta.txt` 记得。

---

## 4. 输出纪律

**做什么**：每次运行都落到一个新的 `OUT` 目录；长任务要能确认它真的还在跑。

- 每次运行都得到一个新的 `OUT`；重跑必须显式地不同。
- 如果 `OUT` 已存在，而且没有被声明为复用，批次脚本必须大声失败。
- 长作业这样起：`setsid nohup ... > out.txt 2>&1 < /dev/null &`。
  `[1]+ Done` 是父进程退出，不是批次结束。核实方法：`pgrep -af 'bash run_'`，再数一下日志里已完成的记录。
- 批次运行期间，不要启动、停止或探测任何和这个引擎共享的东西。

**例子**：你想重跑一次，`OUT` 忘了改。脚本静默覆盖了上一批数据，而你手上只剩一份新的。如果脚本写了"目录存在就报错退出"，你会当场看见。

**为什么**：默认值会无声地覆盖。无声，才是问题。

---

## 5. 共享机器

**做什么**：在多人共用的机器上，只碰自己的东西。这里的每一条都是硬规定。

- 绝不按宽模式杀进程（宽模式 = `pkill -f python` 这种一匹配一大片的写法）。顺序是：`pgrep -af` → 挑准那个 PID → 杀 → 再检查。
- 优先用你自己的启动器写出的 pidfile（一个记着"这次任务的进程号"的小文件）；退而求其次，用一个只有你的项目在用的端口。
- 清理范围 = 本次会话创建的东西。如果归属不清，打印清单然后停下。

**例子**：你起了 8 个 worker，想全部停掉。`pkill -f python` 会顺手杀掉同机器上别人的训练进程。正确做法：`pgrep -af` 列出来，逐行看清命令行，只杀你自己那 8 个 PID。

**为什么**：共享机器上，别人的作业不会自己恢复。

---

## 6. 可复现性

**做什么**：让别人（也包括三个月后的你）能在另一台机器上得到同样的数字。

- 钉住种子；记录每个臂的轮次顺序。
- 论文工件只有在经过一次**从零构建（from-zero build）**之后才被接受：解压提交包，运行文档里的命令，得到相同的页数和相同的数字。
- 把分析脚本留在仓库里；没有脚本的数字是传闻。

**例子**：把提交包解压到一个空目录，只按 README 里的命令跑。如果出来的页数少一页，或者表 3 的某个数字不一样，说明包里少东西。这就是从零构建要抓的。

**为什么**：只在你自己的机器上能跑，不算能复现。

---

## 7. 负面与作废批次

**做什么**：每一个失败或作废的批次（void batch：跑出来了但结果不能用的一批数据），都记一行。

```
batch id | why void | what it can still be cited for | replacement batch
```

- `batch id`：哪个批次。
- `why void`：为什么作废。
- `what it can still be cited for`：它还能被引用来说什么。
- `replacement batch`：替它的是哪一批。

**例子**：
```
exp_0912b | 同机器上有别人的作业，负载不可控 | 只能说明脚本跑得通 | exp_0914a
```

一个没有被记录的作废批次，会在六周后被引用。

**为什么**：你自己会忘。忘了，就会拿它当证据。

---

## 一页速查

1. 每个批次都要有处理臂、相同臂；主张涉及估计时再加 oracle 臂。
2. 先写判据再跑，跑完不许加。
3. `meta.txt` 记全：脚本、commit、模型、种子、分析了哪几轮。
4. 看不到的东西（模型、引擎标志）要声明、守卫、记录。
5. 每次运行一个新 `OUT`；目录已存在就报错退出。
6. `[1]+ Done` 不代表跑完，用 `pgrep -af 'bash run_'` 核实。
7. 共享机器只按 PID 杀，先 `pgrep -af`，杀完再查。
8. 钉住种子，留下分析脚本。
9. 论文工件要过一遍从零构建。
10. 作废批次也要记录，写清还能引用它说什么。
