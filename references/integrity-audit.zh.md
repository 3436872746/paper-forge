# 诚信审计：四层，每层一个负责人

**这一页是干什么的**：它规定谁检查谁，以及一条主张最多能说多强。核心只有一条：没有人审计自己的工作。

**什么时候看它**：

- 你要开始跑一批实验的时候。
- 你要写摘要、标题或贡献列表的时候。
- 你收到拒稿意见、准备改一稿的时候。
- 你要把论文里的数字和结果文件对一遍的时候。
- 投稿前做最后一次检查的时候。

## 1. 四层审计（four layers）

这一节做什么：把"从代码到句子"拆成四个独立检查，每层一个负责人。

| 层 | 问题 | 典型失败 | 产出 |
|---|---|---|---|
| 1. 代码完整性 | 实验是否做了脚本所说的那件事？ | 配置默认值覆盖了 flag；静默覆盖；已经死掉的引擎被报告为成功 | `run_manifest` + 一次抽查重算 |
| 2. 结果 → 主张 | 这个结果是否意味着我们认为的意思？ | 两个变量同时变了；差异低于地板（floor）；聚合方式错误 | 配对统计 + 地板 |
| 3. 论文 → 文件 | 论文报告的数目是否就是文件里的那个数？ | 来自早些批次的陈旧数字；单位或中位数约定的漂移 | 数字到文件的对照表 |
| 4. 引用 → 句子 | 被引工作是否支持这句话？ | 夸大的机制；版本不匹配；二手引用 | 引用定位审计 |

**例子**：脚本里写了 `--batch split`，但配置默认值又把它改回 `full`。这件事属于第 1 层，不属于第 2 层。

**为什么**：分不清层，就会用"重新分析数据"去修一个"数据根本没采对"的问题。

每一层是一次单独的 pass（独立检查轮次）。跑实验的人（或 agent）不在第 2–4 层上签字确认。

## 2. 主张台账（claim ledger）

这一节做什么：给论文里每条主张建一行记录，让句子和证据绑在一起。

保留一个文件（例如 `claims.yml`）。论文中的每一条主张都有一行：

```yaml
- id: C3
  text: "Splitting the cache reduces p99 miss latency by more than the floor."
  status: aligned            # aligned | overstated | not_supported | insufficient
  evidence_artifacts:        # must be non-empty; empty forces status: insufficient
    - runs/20261012_split/metrics.csv
    - scripts/paired_stats.py
  experiment_ids: [E2]
  citation_locators: [sec/table2]
  boundary: "only at 70% load and above"
  verified_by: "second pass, 2026-11-08"
  reason: ""                 # required when status is not aligned
```

**例子**：上面这行说的是"拆缓存把 p99 缺失延迟降到了地板以下"，只在 70% 及以上负载成立。证据是两个文件，边界写清楚了。

**为什么**：没有这一行，主张和证据的关系只存在你的脑子里。

规则：

- **证据为空 ⇒ `insufficient`**，并写明理由。它不能被标成 `aligned`。
- 审计判定的是主张与证据之间的**链接**；它不判定实验本身是否正确（那是第 1 层）。
- 边界为空的主张不算完成。

## 3. 每次运行之前的声明

这一节做什么：跑之前先写下这一轮做什么、不做什么。

在任何批次或分析 pass 之前，记录：

- 本次 pass 使用哪些实验（或"仅文献，无实验"）；
- commit / 脚本哈希；
- 机器与随机种子；
- 本次 pass **不**打算检查什么。

**例子**："本轮：仅文献；commit abc123；机器 A；seed 0；不检查引用定位。"

**为什么**：这把"我忘了加对照组"变成一个可见的遗漏，而不是一个静默的默认值。

## 4. 审阅轮次（review rounds）

这一节做什么：让审阅有上限、有新上下文、有独立判断。

- 每一轮审阅都用**全新的上下文**开始。不要把修复摘要交给审阅者；延续同一个线程往往会抬高分值。
- 给轮次设上限。到达上限时，报告仍然未解决的事项，而不是继续下去。
- 优先**重新表述主张**，而不是再跑一个实验。
- 一次性写出**最强的拒稿备忘**，然后由另一次 pass（不是辩护方）逐条分类：已答复 / 部分答复 / 未解决，并附 file:line 引用。

**例子**：第三轮开始时新建一个会话，只给它论文和台账，不给前两轮的修复说明。

**为什么**：审阅者看过修复清单，就变成了你的合作者。

## 5. 稳定的问题编号（stable issue IDs）

这一节做什么：让每个发现有一个不变的名字，跨轮追踪。

给每个发现编号（`R1`、`R2`、……）并跨轮保留。下一轮必须逐 ID 说明：已修复 / 有意拒绝 / 仍未解决及原因。

**例子**：第一轮发现缓存覆盖不足，编号 R1；第三轮仍叫 R1，状态写"仍未解决：缺 70% 负载下的实验"。

**为什么**：这是唯一能证明在推进、而不是在反复重新发现同样问题的办法。

## 6. 修订白名单（revision whitelist）

这一节做什么：改稿之前，先划定这一轮允许动哪里。

对一轮修订，写下：

- 允许的路径；
- 禁止的操作（例如"不得新增引用""不得新增数值主张"）；
- 最大编辑次数。

**例子**：允许 `sections/limits.tex`；禁止新增引用；禁止新增数值主张；最多 12 次编辑。

**为什么**：边界写下来，改完才能对着 diff 检查。一个新增了主张的修订就不是修订。

## 7. 复述回归（restatement regression）

这一节做什么：每轮改完，重读所有声明主张的句子，看强度有没有偷偷变强。

每一轮修订之后，重读主张陈述（标题、摘要、贡献、结论）。如果其中任何一条漂移得更强，就回退，或记录新的强度为何有支撑。

**例子**：摘要从 "reduces p99 by more than the floor" 变成 "eliminates tail latency"，这就是漂移，要回退。

**为什么**：改一句措辞的时候，最容易顺手把话说满。

## 8. 会话尾声（session epilogue）

这一节做什么：会话结束时，把决定、实验和死胡同写进项目记忆。

在会话结束时，记入项目记忆：

- 做出的决定；
- 跑过的实验（连同它们的 manifest）；
- **死胡同与转向（pivots）**，以及是谁提出的。

**例子**："试过用均值代替中位数，被否。提出人：第二遍审阅。"

**为什么**：死胡同是一等公民。一个失败的想法会变成"禁止重复它"；一个诚实报告的零结果，是下一条主张的原材料。

## 9. 投稿前审计清单

这一节做什么：投出去之前，逐条打勾。

1. 每个主张 ID 都有一个非空的证据列表。
2. 论文中的每个数字都出现在"数字到文件"对照表中。
3. 该表是从原始文件重算的，不是从早先草稿抄来的。
4. 每条引用都有定位，并通过了 `literature-review.md` §6 的四点核查。
5. 没有哪条主张在缺乏新证据的情况下比上一轮更强。
6. 每个未解决的问题 ID 都有状态。
7. "本检查无法确立什么"那一段存在。
8. 有第二个人（或一次全新的 pass）为第 2–4 层签字。

**例子**：第 3 条最容易漏。改过一版数字之后，整张表必须重算一遍。

**为什么**：抄来的表看起来最整齐，也最容易和文件脱节。

## 一页速查

- 四层各有一个负责人，不自己审自己。
- 证据为空，状态只能是 `insufficient`。
- 边界为空的主张不算完成。
- 跑之前先声明：跑什么，不查什么。
- 审阅每轮换新上下文，并且设上限。
- 问题编号跨轮不变，逐 ID 报状态。
- 改稿先写白名单，改完对 diff。
- 改完重读摘要，看强度有没有漂。
- 死胡同要记下来，它下次就是禁令。
- 投前把数字表从原始文件重算。
